# Consistent, extensible recommendation categories

The broad shelves remain stable browsing groups. Specific types and independent attributes describe the item: a Restaurant plus Italian cuisine is displayed as **Italian restaurant**, without creating a combination category. General doctor is narrower than Doctor; a generic doctor mention cannot establish a specialty. These are classifications of saved claims, not verified credentials or entity matches.

## Shared vocabulary and extraction

[`vocabulary.json`](../contracts/rekky/v1/taxonomy/vocabulary.json) is the versioned source of truth. V1 contains 33 types across all five shelves and eight cuisines. Each concept has a stable ID, preferred label, alternative terms (including initial Hindi terms), an optional broader parent, a dimension/display name and compatible entity kinds. Labels and dimensions come from this registry, not generated copy. Some common synonyms have distinct meanings in other contexts; aliases require domain review and are not universal translation rules.

The existing understanding call receives the vocabulary and proposes compatible type/attribute IDs plus source phrases and unit references. The strict schema separates type IDs from facet IDs. Server validation checks IDs, entity kind, known aliases and supporting phrases in this item's represented source units. It handles some explicit negation patterns. Registry metadata resolves a misplaced dimension and parent/child redundancy; it does not turn a broader word into a specific profession. Invalid optional classifications are omitted without losing valid knowledge. These checks do not prove semantic entailment or subject association in every sentence.

Up to three types support hybrid subjects. Up to four attributes are independent of those types. Cuisine is the first normalized attribute dimension; capabilities, suitability and other details retain their existing observations/use-case representation. Additional controlled attribute dimensions can be added in the registry with compatible kinds; generic validation, storage and detail/edit rendering already carry the dimension metadata.

An unfamiliar type/capability can retain a short, source-backed descriptor without minting a global ID. Descriptors remain searchable and visible in detail, with a broad shelf as the compact fallback. Known-category duplicates are omitted from descriptors. This is extensible coverage, not a claim that the seed vocabulary exhausts every recommendation.

## Search and corrections

The classification stores canonical IDs, labels, vocabulary version, origin, derived ancestor IDs and alternative search terms. Postgres generated columns and GIN indexes keep search projections consistent with item updates. Broad Doctor queries include General doctor; the reverse does not apply. Longest-alias matching makes general physician one concept. Recognized types and facets are combined, with remaining lexical qualifiers applied conjunctively. Unclassified legacy memories retain lexical recall. Exact titles remain retrievable even when a title contains a category word.

This is still own-library lexical/category search. It does not establish current service areas, support arbitrary boolean queries or replace the planned semantic retrieval/ranking work. An unknown spelling/language needs an alias or textual match; no multilingual completeness claim is made. Private/deleted/cross-account content stays under the existing owner constraints and pagination.

`GET /v1/taxonomy` requires a signed-in, disclosed account. `PATCH /v1/items/{id}/classification` takes `{ "types": ["place.restaurant"], "facets": ["cuisine.italian"] }` and the current `If-Match`. It validates kind/IDs and limits, sets origin to `user`, increments the item revision and preserves content/audience. Empty selections explicitly keep the broad shelf. The optional **Edit category** control uses this endpoint; ordinary capture adds no decisions. Source deletion preserves saved classifications, while item deletion removes them from retrieval. Existing v2 refinement is idempotent and cannot overwrite the user's assignment; any future general reprocessor must preserve `origin=user`.

## Existing items and vocabulary changes

No background reclassification or paid historical backfill runs. The explicit local maintenance example `classify_existing ITEM_UUID EXPECTED_REVISION TYPE_ID [FACET_ID ...]` validates caller-selected IDs against the item's saved private evidence in a transaction, refuses already-classified items (including user overrides), increments revision and preserves audience/text. It makes no provider call. It is a development maintenance tool, not a public API or an account-discovery mechanism.

New concepts require a reviewed vocabulary change: search existing labels/aliases first, specify meaning and compatible kinds, add aliases and parent where appropriate, add ambiguity/regression cases, then increment the vocabulary version. Never recycle IDs. Label changes, merges or new aliases require a deliberate revision-fenced projection update with redirect/migration rules and preservation of user overrides before rollout; there is no automatic vocabulary migration utility yet. Unmapped descriptors remain on their owning items and do not become a shared public suggestion feed. A future review workflow can propose additions without publishing private source text.

The shared `categorized_recommendation` wire fixture covers the additive response. Older recommendation payloads without classification still render their shelf. See the canonical plan for the remaining organization, semantic-search and quality gates.
