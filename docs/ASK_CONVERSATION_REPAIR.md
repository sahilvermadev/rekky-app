# Ask conversation reliability and local discovery

Status: **repair in progress** (2026-09-28). The first implementation removes the false empty-Library fallback, trims model geography payloads, adds a foreground city/manual area scope and applies role-aware area filtering during retrieval and answer display. These changes still need real-device outcome validation; passing synthetic tests alone does not complete the journey. This refines the [Ask experience plan](ASK_EXPERIENCE_PLAN.md) under the [canonical product plan](REKKY_FLUTTER_PRODUCT_PLAN.md).

## What the observed run established

- An open-ended occasion question returned two places in a different city. Ask received no device-city context, and the current prompt explicitly disallows inferring it. The initial agent search examined only three candidates. This is an input and retrieval design gap, not evidence that the model knew the person's city and ignored it.
- A short city-only refinement **did** carry the prior user turn in `conversation.turns` and the prior answer ID. The second run examined six candidates, including several in the requested city. It ended in `mode: limited` with zero results after the provider adapter failed to return a usable final decision. The exact adapter failure category was not recorded.
- The fallback then classified the refinement as recall and matched its words against candidate **subject names**, so a city-only fragment discarded the candidates already found. The client presented both “the full answer couldn't finish” and “there isn't enough in your Library.” That second claim was false for this run. `search_incomplete` was also set unconditionally by the fallback, rather than reflecting the actual search.
- The work state was a small indefinite spinner below the input. On an empty Ask home, submitting also removed the examples and left most of the screen blank. This gave no useful context, way to adjust geographic scope or recoverable preliminary result.

The second model step may have hit the local 47 KB request guard, timed out, returned an incomplete/non-success response or produced invalid function-call output. We cannot distinguish these from the retained receipt. Geographic payload size is a strong risk, but it is **not a confirmed diagnosis of that particular adapter failure**. Do not replay the person's private request to a provider just to find out.

## Why geographic aliases reach the model

GeoNames aliases live in the server-side geographic catalog to resolve spelling and naming variants to stable area IDs. The Library's `browse` projection currently copies alias arrays for a destination, neighbourhood and regions into **each saved item's** location JSON, allowing the client to match alternate names in its location picker. Ask's `Candidate.locations` copies the entire location JSON from the recommendation. The agent serializes that candidate into previous results and search observations, so it sends display metadata, hierarchy and thousands of alias characters to the model. One observed candidate was about 3.5–5.3 KB, mostly geography; these objects can recur within a turn. The aliases are useful to the geographic resolver and picker, but they add little to reasoning about whether a recommendation fits.

The immediate fix is a **separate, compact Ask projection**, not removing geographic identity from saved knowledge. Return evidence IDs/text plus location role, canonical label, resolved area/city IDs and resolution status. Keep the full catalog, aliases and containment logic in Rust/Postgres. A typed geographic search tool resolves “Bangalore” and “Bengaluru” locally and applies owner, role and area constraints before pagination. The model sees a concise result such as `venue · Bengaluru · area_id`, never the alias array or raw hierarchy. Measure byte/token budgets at every agent decision and bound repeated evidence. In a later Library API cleanup, move alias lookup to one shared catalog/search response rather than embedding the same aliases in every recommendation; preserve offline/manual picker behavior before removing that projection.

## Conversation contract and user experience

1. **Visible local context.** For open-ended *discovery*, ask for foreground approximate/When-in-Use location at the moment local results become useful, not on app launch. Resolve to a coarse city on the device where feasible; send a validated city label/ID and source, not a coordinate history. Show an editable `Near Delhi` scope above the answer and while working. An explicit city in the request wins; an explicit `Everywhere` removes the local constraint. If permission or resolution fails, offer manual city choice or `All locations` and label the scope honestly. Do not use device city as evidence that a provider serves an area, or constrain personal recall such as “who was that driver?” by current city. Do not request background location.
2. **Structured working state.** Persist a bounded, owner-scoped effective request: intent, occasion/need, hard constraints, optional preferences, geographic scope and its provenance, selected/excluded IDs, unresolved questions and cited answer references. A follow-up such as “in Delhi” modifies the prior discovery request; the UI shows the combined interpretation while retaining the user's actual words in history. The latest explicit request overrides earlier and device context. Re-fetch current authorized evidence; stale revisions and revoked access cannot survive a turn.
3. **Agent with useful tools.** Keep one bounded agent first. Give it typed `resolve_area`, `search_knowledge` (structured role/area filters plus lexical clues), `inspect_evidence` and `present_answer` capabilities. Exact recall may use a direct deterministic path. For discovery, apply access and hard geography before ranking; use model judgment for suitability, tradeoffs and consequential clarification. Semantic retrieval/reranking are candidates for measured improvement, not automatic additions. A tool result should be compact, predictable and evidence-linked. Compare a proper Responses function-call continuation with the current repeated fresh requests while preserving `store:false` and Rekky-owned private state; do not adopt durable provider-side conversation storage merely to simplify implementation.
4. **Graceful failure.** Record content-free error categories (payload guard, timeout, HTTP status class, incomplete model output, malformed function call, answer validation), stage timing, tool names, candidate counts and bytes/tokens. Never log raw questions, notes, contacts or location coordinates. Preserve any validated, relevant candidates if synthesis fails; otherwise retain the previous answer and show a clear retryable failure. An adapter failure must never become “no recommendations saved.” Retry within the same bounded operation only when safe and measurable; no open-ended extra paid calls.
5. **Conversational surface.** On submit, show the understood request and visible city scope. Keep the previous answer usable during refinement. Indicate only a true observable stage (for example, searching saved knowledge or checking fit) if the backend emits that event; otherwise use one calm work state, Cancel and a delayed “taking longer” message. Show a validated preliminary result only when it is actually available. Avoid fabricated reasoning, pseudo-progress and a full-screen blank wait. On success, lead with the most helpful answer or a consequential clarification, with cited saved evidence and compact alternatives. On failure, explain the interruption without implying an empty Library.

This design follows current [official OpenAI documentation on agent/runtime choices](https://developers.openai.com/api/docs/guides/agents), [conversation state](https://developers.openai.com/api/docs/guides/conversation-state), [tool contracts](https://developers.openai.com/api/docs/guides/function-calling) and [trace/evaluation practice](https://developers.openai.com/api/docs/guides/agent-evals). Multi-agent orchestration is not a quality goal by itself; add complexity only when controlled evaluations show a better user outcome. Platform guidance supports [foreground approximate location on Android](https://developer.android.com/develop/sensors-and-location/location/permissions) and [When-in-Use authorization on iOS](https://developer.apple.com/documentation/CoreLocation/requesting-authorization-to-use-location-services).
