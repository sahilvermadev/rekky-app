# Ask conversation reliability and local discovery

Status: **conversation redesign required** (2026-09-28). The first repair removed the false empty-Library fallback, trimmed model geography payloads and added a city scope, but a real-device date conversation exposed retrieval, geographic, reliability and presentation failures. Passing synthetic tests alone did not complete the journey. This refines the [Ask experience plan](ASK_EXPERIENCE_PLAN.md) under the [canonical product plan](REKKY_FLUTTER_PRODUCT_PLAN.md).

## What the observed run established

- An open-ended occasion question returned two places in a different city. Ask received no device-city context, and the current prompt explicitly disallows inferring it. The initial agent search examined only three candidates. This is an input and retrieval design gap, not evidence that the model knew the person's city and ignored it.
- A short city-only refinement **did** carry the prior user turn in `conversation.turns` and the prior answer ID. The second run examined six candidates, including several in the requested city. It ended in `mode: limited` with zero results after the provider adapter failed to return a usable final decision. The exact adapter failure category was not recorded.
- The fallback then classified the refinement as recall and matched its words against candidate **subject names**, so a city-only fragment discarded the candidates already found. The client presented both “the full answer couldn't finish” and “there isn't enough in your Library.” That second claim was false for this run. `search_incomplete` was also set unconditionally by the fallback, rather than reflecting the actual search.
- The work state was a small indefinite spinner below the input. On an empty Ask home, submitting also removed the examples and left most of the screen blank. This gave no useful context, way to adjust geographic scope or recoverable preliminary result.

The second model step may have hit the local 47 KB request guard, timed out, returned an incomplete/non-success response or produced invalid function-call output. We cannot distinguish these from the retained receipt. Geographic payload size is a strong risk, but it is **not a confirmed diagnosis of that particular adapter failure**. Do not replay the person's private request to a provider just to find out.

## Date conversation audit, 2026-09-28

The owner’s recent Ask receipts show a completed weekend answer with zero results and a broad “food, class/workshop, or outing?” clarification; a date refinement repeated a similarly broad question after inspecting only one saved item. Two subsequent runs failed after one and two model decisions respectively. The final short “food” refinement completed with one result, Evo, after inspecting only Evo and Manu. The failed receipts retain no failure category or content, so their exact cause cannot be attributed to the model, the network, validation or a deadline.

The phone’s coarse locality was **New Delhi** (`geonames:1261481`). The Big Chill Cafe’s saved venue is **Connaught Place, Delhi** and its indexed scope includes Delhi and the New Delhi administrative district, but not that New Delhi city ID. The current exact-area check can therefore exclude a relevant Delhi restaurant while admitting Evo, whose saved venue geography is unresolved, as an unknown-area candidate. The final answer title nevertheless called Evo a “Pizza date idea in Delhi”; the title must not turn an unknown venue location into a supported claim. A default phone locality must resolve to a useful metropolitan search scope; explicit named neighbourhoods and cities may intentionally be narrower. The user should not have to understand or correct this identity mismatch.

This is more than a prompt problem. At the time of the initial repair, the model could choose a narrow lexical search before learning what the Library contained, had no compact coverage overview, and could ask about options Rekky had no saved evidence for. The answer schema forced a title, result list or clarification rather than a natural reply that could offer a supported part of a request and name the missing part. The Flutter surface then showed one answer at a time with “Previous answer” and “New question” controls, so it read like a sequence of pages instead of a conversation. The later continuous thread and full-screen layout supersede that UI state.

## Why geographic aliases previously reached the model

GeoNames aliases live in the server-side geographic catalog to resolve spelling and naming variants to stable area IDs. The Library's `browse` projection still copies alias arrays for a destination, neighbourhood and regions into **each saved item's** location JSON, allowing the client to match alternate names in its location picker. Before the first repair, Ask serialized `Candidate.locations` wholesale into model-facing previous results and search observations, sending display metadata, hierarchy and thousands of alias characters. One observed candidate was about 3.5–5.3 KB, mostly geography. The aliases are useful to the resolver and picker, but add little to reasoning about whether a recommendation fits.

The first repair added a **separate, compact Ask projection**, preserving geographic identity in saved knowledge. Model-facing results now carry evidence IDs/text plus location role, canonical label, resolved area ID and status, without alias arrays or hierarchy. The full catalog and role-aware containment remain in Rust/Postgres; the typed geographic search resolves names locally and applies area constraints before pagination. Measure byte/token budgets at every agent decision and bound repeated evidence. A later Library API cleanup may move alias lookup to a shared catalog/search response rather than embedding aliases in every recommendation; preserve offline/manual picker behavior before removing that projection.

## Conversation contract and user experience

1. **Quiet, correct local context.** For open-ended *discovery*, request foreground approximate/When-in-Use location when useful, not on app launch. Resolve locally to a coarse metropolitan scope, with provenance and an honest unresolved state; send no coordinate history. Do not show a persistent `Near New Delhi` chip in the Ask conversation. Use the area implicitly in retrieval and natural answer language only when relevant; the person can say “actually in Bangalore,” choose a place from a secondary control, or use `everywhere`. An explicit place wins. If permission or resolution fails, ask for an area only when needed, or search without a local constraint and say so. Recall is never constrained by the phone’s location. Do not infer a provider’s service area from device location or request background location.
2. **Structured working state.** Persist a bounded, owner-scoped effective request: intent, occasion/need, hard constraints, optional preferences, geographic scope and its provenance, selected/excluded IDs, unresolved questions and cited answer references. A follow-up such as “in Delhi” modifies the prior discovery request; the UI shows the combined interpretation while retaining the user's actual words in history. The latest explicit request overrides earlier and device context. Re-fetch current authorized evidence; stale revisions and revoked access cannot survive a turn.
3. **Agent with knowledge of its own coverage.** Keep one bounded agent first. Add a compact, authorization-scoped `library_overview` reporting available categories/capabilities and known, unknown or conflicting local geography; this is an inventory, not a list of presumed user interests. Give it typed `resolve_area`, `search_knowledge` (structured role/area filters plus lexical/semantic clues), `inspect_evidence` and `present_answer` tools. For open-ended local discovery, browse broadly in the resolved scope before deciding to clarify; search exact names directly for recall. Apply access and hard geography before ranking, then let the model judge suitability and tradeoffs. A clarification is warranted only when its answer could materially change a useful response **and** the Library contains evidence for the branches. A missing category must not become a question asking the person to choose it. Implement proper stateless Responses function-call continuation, including returned output and function results, instead of treating each decision as a fresh user JSON request; retain `store:false` and Rekky-owned private state.
4. **Useful partial answers and graceful failure.** Extend the answer contract to carry a short conversational reply, grounded recommendation IDs/evidence, explicit missing parts and at most one consequential follow-up. For “food plus activity” with only dinner evidence, give the best supported dinner option and say no saved local activity was found; never invent an activity or drop the dinner option. An eventual external search may fill gaps with clearly separate provenance, without representing a public result as a friend’s endorsement. Record content-free error categories (payload guard, timeout, HTTP status class, incomplete model output, malformed function call, answer validation), stage timing, tool names, candidate counts and bytes/tokens. Never log raw questions, notes, contacts or coordinates. Preserve validated partial results; otherwise keep the prior turns and show an inline retry. A failed adapter call must never become “no recommendations saved.” Bound all retries and paid calls.
5. **One continuous conversation.** Replace the current-answer slideshow with a scrollable thread: compact user turns, Rekky’s plain-language replies and embedded evidence-linked recommendation cards. Keep recent turns visible and older turns available by scrolling, with the composer pinned above the system gesture area. Hide the primary app bar and navigation capsule during the full-screen conversation. Remove persistent `Previous answer`, `New question`, edit-pencil and area-chip clutter from the message column; keep only a back arrow in the header, and allow a natural “actually in …” correction. A new home question starts a new thread while a valid previous one remains resumable. Keep earlier turns and cards on screen while a follow-up runs. Show only genuine work state or a validated preliminary result; no fabricated thinking/status. On failure, show a retry inside that turn and leave the preceding conversation intact. Do not clear the screen to a blank home after a follow-up.

For the observed date request, a useful reply would lead with a saved Delhi dinner option such as The Big Chill Cafe and its cited experience, then say that no saved local activity was found. It would not ask the person to choose among classes, workshops and outings that the available knowledge cannot support. A future, separately labelled public-place search could fill the missing activity; until that tool and its source/freshness checks ship, Rekky must present the dinner part without pretending the date plan is complete.

This design follows current [official OpenAI documentation on agent/runtime choices](https://developers.openai.com/api/docs/guides/agents), [conversation state](https://developers.openai.com/api/docs/guides/conversation-state), [tool contracts](https://developers.openai.com/api/docs/guides/function-calling) and [trace/evaluation practice](https://developers.openai.com/api/docs/guides/agent-evals). Multi-agent orchestration is not a quality goal by itself; add complexity only when controlled evaluations show a better user outcome. Platform guidance supports [foreground approximate location on Android](https://developer.android.com/develop/sensors-and-location/location/permissions) and [When-in-Use authorization on iOS](https://developer.apple.com/documentation/CoreLocation/requesting-authorization-to-use-location-services).

## Conversation and exploration extension

The [generative UI implementation spec](ASK_GENERATIVE_UI.md) extends this repair: the conversation and a complete collection browser are two connected surfaces inside Ask. Natural-language “everything in …” requests create server-backed views with exact filters, counts and pagination. A direct promptless browse entry still needs a placement that does not clutter the solo Ask home or conversation header. The model selects a native composition; ordinary view interactions need no model call. Network exploration belongs in Ask, not a second browser inside Library, and remains dependent on real reciprocal authorization. This does not replace the geographic, conversation and reliability repairs below.

The existing `library_overview` proposal is named `knowledge_overview` in the new contract to reflect own plus future shared knowledge; it is the same capability, not a duplicate tool.
