# Voice transcription bridge (F-01.1, partial)

This slice connects a ready local M4A draft to a private server transcript. It stops before automatic understanding, Library publication or friend access. No audio is uploaded automatically: the signed-in user must tap **Transcribe** and affirm the separate OpenAI processing disclosure. The new-product Rust backend holds upload bytes in memory for a synchronous `gpt-transcribe` request and does not persist server audio. Its `OPENAI_API_KEY` is backend-only, and `OPENAI_TRANSCRIPTION_ENABLED` controls whether the adapter accepts requests. The local draft is marked for deletion only after a usable transcript is committed and acknowledged; cleanup retries at later app launches if local file removal fails.

The disclosure says OpenAI's API data is not used for model training by default unless the API account opts in, and that default abuse-monitoring logs may contain content for up to 30 days, with stated longer-retention exceptions. These are provider policies, not Rekky's local audio retention promise. Verify the actual API account's data-sharing settings and regional route before a broader pilot. References: [file transcription and supported M4A input](https://developers.openai.com/api/docs/guides/speech-to-text), [API data controls](https://developers.openai.com/api/docs/guides/your-data), [GPT-Transcribe price](https://developers.openai.com/api/docs/models/gpt-transcribe).

## Contract and safety boundaries

- `GET/POST /v1/me/voice-transcription-permission` exposes and changes the separate permission generation. Enabling requires disclosure v1; withdrawal cancels in-flight jobs and fences their late results. Completed private transcripts remain.
- `POST /v1/voice-drafts/{draft_id}/transcribe` accepts M4A binary from one signed-in account, enforces a seven-day client capture timestamp, 5 MiB body limit, a first MP4 box check, a rolling 24-hour reservation limit of 12 new draft IDs per account and 100 globally, and at most three attempts per draft. A matching retry returns the already committed transcript; changed audio conflicts. These are pilot limits, not measured production capacity or a reliable audio-duration parser.
- The private transcript commits to `source_texts` under a voice capture with `transcript_ready` status. No knowledge item is created, so a friend's Library/Ask never receives it. `GET /v1/voice-captures` lists only the owner's retained transcripts; the existing source-delete endpoint removes one on request.
- The provider adapter does not log audio, transcript text or provider responses. Provider errors and unusable empty/nonalphabetic responses leave the local draft available for retry. Basic text validation cannot detect every truncation or mistranscription; the labelled audio quality gate remains open.
- If withdrawal is acknowledged while a provider call is in flight, a late result cannot commit. A request already dispatched may still have reached OpenAI; Rekky cannot recall it or promise immediate deletion of provider-side logs.

## Evidence and open work

Rust/Postgres tests cover the separate consent gate, realistic binary upload, owner isolation, idempotent receipt recovery, withdrawal fencing, retained transcript and request budget. Flutter tests cover the binary wire shape, local acknowledgement/deletion, withdrawal cleanup and migration of the user's existing draft metadata. Android builds and the physical phone showed the pre-upload disclosure while preserving the user's approximately 231 KB local draft. The consent was declined during inspection: **no real provider transcription was run** and that draft was not uploaded. On 2026-09-25 the user authorized enabling transcription on the local pilot backend before reviewing the provider account's data-sharing policies. The adapter's enable switch is not an audit marker. [Backend, Android and iOS build CI](https://github.com/sahilvermadev/rekky-app/actions/runs/36172036023) passed; iOS runtime, local-delete timing under storage failure, account data-sharing settings, transcript fidelity, offline authenticated capture and end-to-end knowledge extraction still need evidence. No F-01 gate is complete.

**First live pilot, reported 2026-09-26:** The user reports that transcription worked. Local Postgres has one completed voice job (one attempt), an owner-only 265-character transcript source under a `private` voice capture, and zero knowledge items for that capture. Android's protected draft directory contains only an older draft with a different ID; the completed job's draft file is absent. This supports the normal saved-transcript/audio-cleanup path. We did not observe the exact deletion timing, compare the transcript to the original audio before deletion, or exercise a real provider failure/retry. The older draft remains available on the phone. The next integrated slice must turn the private transcript into reviewable knowledge and own-Ask results without automatically publishing it to friends.
